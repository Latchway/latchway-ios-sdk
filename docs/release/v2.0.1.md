# Latchway iOS SDK 2.0.1

Error diagnostics patch for the fresh shared-account SDK. No storage migration,
wire protocol change, Firebase dependency, or attestation bypass is introduced.

- Preserve every existing canonical Problem field through the public native error
  model: safe detail, retry timing, feature, field errors, supported protocol
  versions, operation correlation and diagnostic reference.
- Add `LatchwayProblem.decode(from:response:)` and `decode(from:)` for bounded,
  validated parsing in custom HTTP integrations. Unknown optional members are
  ignored, not propagated into logs or retry decisions.
- Distinguish temporary discovery outages from unsupported identity capability.
  Malformed HTTP error bodies retain safe status and request ID via
  `LatchwayHTTPResponseError(statusCode:requestID:)`.
- Foundation Models preserves canonical HTTP failures; rate limits carry the
  typed `LatchwayProblem` in `metadata["latchway_problem"]` and a real reset date
  when supplied. Invalid bodies never expose raw upstream text.
- Responses stream failure/truncation retains request and generation correlation,
  without replaying partial answers or executing incomplete tool calls.
- New diagnostics use additive Error structs, preserving exhaustive switches over
  existing public error enums. Known optional Problem fields reject null or
  malformed values; request IDs use the same safe grammar as the other SDKs.
- LatchwayChat now displays validated gateway details and field errors explicitly;
  general error descriptions continue to omit response-body text.

Use SwiftPM tag `v2.0.1` or CocoaPods `Latchway/AppAttest`, `2.0.1`. The optional
Foundation Models product still requires Xcode 27 / Swift 6.4 and OS 27. The core
SDK minimum remains iOS 15 / macOS 12. Pair embedded RN apps with
`@latchway/react-native@2.0.1`.

## Verification and known limitation

118 affected Swift tests and 20 Foundation Models tests on an iOS 27 simulator
passed. Release-mode consumer compilation verifies that existing exhaustive
switches remain source-compatible. The example build and four documentation
tests passed. No fresh physical App Attest proof is claimed.

The full suite exposed a pre-existing cancellation-test race:
`testCancelledInitialProducerCannotRestoreAfterLogoutFence` can observe
`cleanupRequired` while cancelled sign-in cleanup is still in progress instead
of the expected `loggedOut`. It reproduces from unchanged 2.0.0 source. That
single test was excluded from the final affected-suite run; lifecycle code and
its test assertions were not changed by this diagnostics patch.
